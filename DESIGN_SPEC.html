Autonomous MLX Kernel Optimization

A harnessed search loop for faster Metal kernels, without changing the model.

Shivam Garg · Design spec · August 2026

What this is

This system speeds up MLX models on Apple Silicon without changing what they compute. MLX is Apple’s array library for running neural nets on a Mac. Under the hood, each math op (a norm, a matmul, attention) is a Metal GPU kernel: a small GPU program the chip actually executes. Those library kernels are already strong. The leftover speed is usually not “rewrite softmax.” It is fusing adjacent ops so a vector never goes out to memory and back, and specializing how a kernel is launched for the shapes you actually run.

How the speed happens: an LLM and a measurement harness take turns in a loop. The LLM proposes a rewritten kernel, the harness checks that the model’s outputs are unchanged and times it, and only rewrites that are both correct and faster survive. Nothing about this is specific to one architecture; the loop optimizes whatever graph the model actually ran. What it finds depends on the workload you hand it, because kernels are shape-specific: a kernel tuned for one batch size or context length can be slow at another, and different phases of the same model (a long prompt versus generating one token at a time) lean on different kernels entirely. Changing the workload changes what gets optimized and how, so the manifest pins the workloads and the system tunes for exactly those.

Why hand this to an agent: writing fused or shape-specialized kernels is the job a model performance engineer does by hand, and it is checkable work. Same inputs, same numeric outputs, lower latency on a real Mac. That checkability is what makes the loop safe: the harness intercepts the model’s op calls, compiles the Metal, checks outputs still match the original, times only the runs that passed, installs the winners into the model, and refuses to keep a cheat.

Hard constraints. Dtypes and quantization stay frozen. The optimizer is not allowed to make the model cheaper by changing its math. Faster-but-wrong is discarded. Correct-but-slower does not ship into the model.

Who does what

The work splits into two roles, kept strictly apart, so the one proposing changes never grades its own work.

The harness (ordinary code) loads the job, intercepts op calls, traces, cuts regions, builds the starting Metal, evaluates every hypothesis out of process, runs correctness, times workloads, installs a keep by swapping in a generated replay wrapper, retraces after a region closes, writes the artifact, and enforces the keep law. It never “decides a fusion looks good.”

The LLM judge proposes work. It sees metadata only: graph summaries, IO schemas, compiler errors, bench rows, how far the current kernel sits from the hardware limit. It never sees weights or activations. It never overrides a failed check. It writes one Metal body at a time, plus a short hypothesis, then waits for the verdict before the next one.

The loop

The picture is the whole job. One hypothesis is tried at a time, each one small evaluated change to a kernel. Fail and climb return to the queue. A ship goes through bind and e2e before it is allowed to stay. Closing a region retraces and walks the next cut. The job ends with files you can load without the harness.

The autotuner loop. The harness owns measurement, correctness, bind, and the artifact.

Job in: the manifest

You never talk tensors to the judge. You submit a manifest, the job’s contract:

  • The model: a path to a Python file that defines build(). build() takes no arguments, resolves its own paths relative to its file, and returns the model as a self-contained, repeatable callable: one call is one unit of work, state included. It must work from a fresh import in a subprocess, because hypothesis evaluation is out of process; a live object or a closure can never be the model.
  • Workloads: the real input shapes this model will see, as a list. A workload holds one input spec per positional argument of the model, each a shape plus a dtype; a dim named in a shape (an “L” instead of a number) is sweepable. A workload may carry a name; names exist for the report and the logs, and the harness attaches no meaning to them. Workloads are the only shapes we optimize for.
  • Stateful workloads live in build(), not in the manifest. A decode job is a wrapper whose one call is a repeatable step with the cache handled inside, because a hand-built KV cache is a different graph (padding, slice, concat) than a stepped one. A decode wrapper that still runs a full-sequence matmul is a bad wrapper, and the trace will price the wrong graph.
  • A sweep policy for correctness (other sizes we must not silently break). Dims named in workload shapes (an “L”, not a number) are sweepable; integer dims are model constants and are never swept. Omitted, a named dim defaults to 1, a prime, a non-multiple of 32, and one large size.
  • Nothing about dtypes or quantization. They are not knobs: frozen by law, recorded in the report.
  • Numeric tolerances (rtol / atol) for assoc-preserving compares against the original model. Optional; defaulted and recorded, like the assoc-changing gate’s κ and floor.
  • A trial budget (max trials per region, max trials for the whole job). Optional; defaulted and recorded.
  • The chip is auto-detected; nothing to declare.

The harness materializes workload tensors (synthesis seed fixed by the harness and recorded, not supplied), pins the device, and only then starts measuring. The first eval of each workload is warmup (Metal compile) and is thrown away.

The whole vocabulary, and an example derived from it:

manifest:
  model:  ./model.py            # defines build() -> a self-contained, repeatable callable
  workloads:  [workload, ...]
  sweep:  {DIM: [sizes]}        # optional; named dims only, defaulted if omitted
  tolerances: {rtol, atol}      # optional; assoc-preserving gate
  budget: {per_region, total}   # optional

workload:
  inputs: [input, ...]          # one per positional argument of the model
  name:   label                 # optional; report label only, no semantics

input:
  {shape: [8, "L"], dtype: float16}     # a dim named "L" is sweepable; integers are fixed
model: ./model.py

workloads:
  - inputs: [{shape: [8, "L"], dtype: int32}]   # one entry per model argument
    name: midbatch

  - inputs: [{shape: [1, 1], dtype: int32}]
    name: decode        # build() wraps the stateful step inside the callable

sweep: {L: [1, 7, 512, 4096]}

Trace

Tracing works in two passes per workload: one records what the model does, one measures what a step costs. They are separate because the recording machinery is overhead that would poison any timing.

Each workload gets its own passes. Different input shapes can produce a different graph, so nothing recorded on one workload is assumed about another.

Apple’s GPU tools were tested for this job, not assumed away. A Metal capture (.gputrace) holds the GPU commands for Xcode to replay by hand and contains no timings at all. Instruments can be scripted (record a run, export XML), but its tables stamp command buffers rather than ops, and MLX batches many ops into one buffer; forcing one op per buffer lines the stamps up with the op record, at the cost of changing the very scheduling being measured. So those tools stay available as an occasional cross-check, and ranking uses the replay clock described with regions.

Pass 1: record what the model does

The recorder is one Python trick. Every MLX function that returns arrays (mx.add, mx.matmul, mx.fast.rms_norm, and so on) is reassigned to a version that writes down the call and then runs the original. The operators and methods on arrays are wrapped the same way, so x + y, 2.0 * x, slicing, and writing into a slice (x[i] = v) are all seen. The model’s code is never parsed or modified; it runs as-is and does not notice.

Each recorded call becomes one node: the op, the shapes and dtypes of its inputs and outputs, the identities of the actual arrays that flowed through, any non-tensor arguments, and which module instance it ran inside (module calls are wrapped too, so two copies of the same layer are never confused, even when the data decides which one runs). A node’s module-and-position address is where a replacement kernel can later be installed, so what the recorder can see is exactly what the system can ship. Connections are derived afterward: whoever produced an array links to everyone who consumed it, and the record keeps which arrays the step returned. The module tree itself is only context for those addresses; regions are built from the recorded ops alone.

The recording pass never evaluates. MLX is lazy: calling an op returns a promise of the result, and real GPU work happens only when something is evaluated. One un-evaluated pass through the model therefore yields the complete op list with no GPU time spent and no tensor memory filled, and every array can be held for the whole pass, which keeps identities unambiguous.

Completeness is checked, not assumed. Every array feeding a recorded call must be a workload input, a model weight, or the output of an earlier recorded call, and the step’s outputs must come from recorded calls. An array that appears from nowhere means some MLX entry point was not wrapped, and the trace stops and names the call that received it. Two smaller rules exist for the same reason: the recorder installs before the model’s file is imported (a file that imported a function earlier would keep the unwrapped original), and mx.compile is wrapped too, so a model that compiles part of itself records that part as one opaque call. Ops hidden inside it cannot be regions; everything else still can.

A recorded call sometimes expands to more than one internal GPU kernel. That is fine: the call is the unit of record on purpose, because it is also the unit a wrapper can replace.

Pass 2: the step clock

The step clock is the honest cost of one call of the model on a workload: warm up, run the full model several times, take the median. It is measured with the recorder completely removed, since the recorder is Python overhead on every op and no timed number is ever taken with it installed. Every later “share of the step” divides by this number, and the final report’s before-and-after uses it.

The stage, as code:

tracer.install()                    # reassign mx.*, mx.fast.*, array operators/methods,
                                    # mx.compile; wrap module __call__s. Before model import.
model = import(manifest.model).build()
for w in workloads:
    with tracer.armed(w):
        outs = model(*w.tensors)     # pass 1: record. Lazy, no eval, no GPU work
    trace[w] = tracer.freeze(outs)   # edges, liveness, completeness check; drop array refs
    tracer.disarm()
    step_ms[w] = median(evals(model, w))   # pass 2: step clock, recorder removed

Regions

A region is a stretch of the recorded op list that the loop will try to replace with one kernel: a run of consecutive recorded calls, plus everything the record knows about what flows in and out of it. There is no built-in list of fusions for known architectures, and the module tree plays no part; candidates come from whatever this model’s recorded ops actually allow.

Every value produced inside a stretch is either used only inside it, or needed by the rest of the model. The first kind can vanish into the fused kernel; that is where the win comes from, since the value stops making a round trip through memory. The second kind is live: a residual stream that later layers read, a value written into a cache, the step’s own outputs. A live value does not forbid fusion, but the kernel must still write it out; deleting a store the rest of the model reads is just a wrong answer. One case has no fix: a live value that the model’s own Python code consumes partway through the stretch (stored into a cache object mid-sequence, say). The wrapper cannot reach a reference the model has already kept, so the region either ends there or leaves that value to the library.

Reshapes, transposes, squeezes, and slice reads move no data; they only reinterpret layout. They never end a region: they are absorbed, and the fused kernel’s indexing does the reinterpreting. A reinterpreted value is written out only if it is live in two different layouts, which is the live rule again. A stretch that is nothing but views is not a region; there is no work in it to speed up. Writing into a slice of an existing array is different: it edits memory something else may be holding, so it always ends a region for now.

One identity rule before building: all copies of the same op sequence across the model are one region. A transformer has the same norm-then-projection stretch in every layer; those are priced together, share one hypothesis history, and ship together through one wrapper. That is also what makes small stretches worth anything: 0.3% of the step looks like noise, but 0.3% times 32 copies is a tenth of the step.

What a region carries:

region:
  ops:       [call, ...]          # a run of consecutive recorded calls
  copies:    32                   # the same sequence elsewhere in the model
  inputs:    [array, ...]         # everything the stretch reads from outside
  outputs:   [array, ...]         # everything the model reads back, live values included
  workloads: [midbatch, decode]   # where the sequence fires
  p:         0.19                 # share of the step (pricing, below)
  T_orig:    region clock, ms       # pricing, below
  roofline:  T_roofline, s_max      # physics limit (next section)
  bound:     memory | compute | launch    # whichever limit binds

Building the candidate list is two moves. First, every distinct recorded op is a candidate on its own. Second, grow chains: extend through the next recorded ops for as long as every value produced so far either dies inside the stretch or can be written out as an extra output. A data edge to the next op is not required, so neighbors that merely share an input can merge too: three projections reading the same normed vector become one kernel. Keep the maximal chains and their prefixes. Not every subset is enumerated. After pricing (below), anything whose copies together fall under a floor, about 2% of the step, is dropped: below that, even a looped clock cannot certify a win against noise, and the budget is better spent elsewhere. The floor is also why a tiny op never stands alone but still matters as part of a bigger stretch: a norm-plus-projection chain and the projection alone can both be candidates, while the 40 µs op between them only rides along.

A stretch is rejected as a region if any of these hold:

  • There is no place to install a wrapper on it (no enclosing module scope can host a generated replay wrapper).
  • It would delete a live value it cannot write out.
  • It mixes CPU and GPU work.
  • It would need a dtype or quantization change.

Pricing and ranking

Once the candidate cuts exist, one more recorded pass per workload keeps just the arrays at their edges: each region’s real inputs, and the library’s outputs for them. With fixed inputs a rerun would reproduce these byte for byte, so saving changes cost, not truth. Every later correctness check and region timing runs against these saved tensors, and the rest of the model stops being re-paid thousands of times per region.

There is no per-op GPU counter to read, and forcing the GPU to finish after every op makes tiny ops look far more expensive than they are in a real run. So a region is timed as a unit: run its recorded ops on the saved inputs, looped until there are tens of milliseconds of work, and take the median. Its share of the step is p = region time × copies / step time.

Two details keep that loop honest. It cycles through several distinct input sets, enough that the data cannot just sit in the GPU’s cache, because a cache-resident loop makes memory traffic look free, and deleted memory traffic is the main thing fusion buys. And every iteration’s outputs are kept in the final evaluation, because laziness would otherwise notice the results are unused and skip the work entirely.

If the model picks its ops based on the data (mixture-of-experts routing, any branch), the trace holds only what actually ran on this workload, and shares are computed from that. Paths the workload never took are a correctness question, handled later by the sweep, not something to pretend into the ranking.

Each candidate region also gets a quick physics estimate before any budget is spent: from the bytes it must move and the math it must do, how fast could an ideal kernel be, and how much op-to-op traffic could fusing delete. A region where even the ideal kernel barely beats what is already there is skipped. This is how the workload you declared decides what gets optimized: the workloads set the room, and the harness drops regions that have none. The arithmetic behind it (the roofline) is the next section.

Candidates overlap on purpose; a chain and its prefix share ops. Rank by p. Ties go by the recorded bound: memory-bound first, then launch, then compute, because fusion has the most to offer where the cost is traffic. Overlap resolves itself downstream: if a bigger cut ships, the singletons inside it are skipped; if it never ships, they still get their turn.

A sequence that fires in more than one workload (the same norm at two shapes) is still one region, ranked by its combined cost across those workloads. The first attempt is always one kernel that is correct everywhere and faster everywhere. If that cannot ship, the judge may specialize per workload; the installed wrapper then picks a kernel by shape at runtime and falls back to the library for any shape none of them covers.

The stage, as code:

candidates = []
for seq in singleton_ops(trace) + grown_chains(trace):   # the build rules above
    if rejected(seq): continue                           # the four conditions above
    candidates.append(group_copies(seq))                 # all copies -> one region
for w in workloads:
    with tracer.armed(w, retain=boundaries(candidates)):
        mx.eval(retained(model(*w.tensors)))             # save real inputs + outputs, once
for r in candidates:
    r.p = region_clock(r) * r.copies / step_ms           # looped replay, inputs rotated
candidates = [r for r in candidates if r.p >= floor and r.roofline.has_room]
ranked = sorted(candidates, by=combined_p, tie=memory > launch > compute)
tracer.uninstall()                                       # the model is native again

Roofline

The roofline is a region’s physical speed limit on this chip: how fast the work could possibly go if the hardware were used perfectly. It is computed during pricing, for every candidate region: the chip’s peaks are measured once at job start with a microbenchmark, and the rest is arithmetic over recorded shapes. The judge is told it, never asked for it. It answers two questions: when is more cleverness wasted, and why can fusing win even when each op already looks fast on its own.

The bytes-and-launch part of the limit is measured rather than computed: a probe kernel, one launch that streams the region’s boundary bytes, is timed beside the region in the same paired window, and the region’s time over the probe’s is the headroom. A dependent kernel pays its launch and its stream in series, and the peak from a large pass is out of reach at the sizes a decode step is made of, so the arithmetic alone overstates headroom by a third there; and two clocks taken minutes apart on a machine whose speed moves cannot be divided. The flops term stays arithmetic against the matmul peak. The same probe is clocked beside every kernel in the sandbox, so the close rules below compare each kernel to the floor measured next to it.

The limit is whichever resource runs out first: moving the bytes, doing the math, or just launching kernels.

bytes      = region inputs + outputs          # NOT the intermediate round trips
flops      = sum over ops, from op and shape  # a matmul is 2*M*N*K, a norm a few passes over N
bandwidth, peak_flops = microbenched on this chip at job start, not read off a spec sheet
T_mem      = bytes / bandwidth
T_compute  = flops / peak_flops
T_launch   = kernels_still_fired * a few us
T_roofline = max(T_mem, T_compute, T_launch)  # whichever resource binds first
s_max      = T_orig / T_roofline              # ceiling on this region's speedup

Whichever term wins the max is recorded as the region’s bound: memory, compute, or launch. The tie-break in ranking reads it, and the judge is told it, because the right move depends on it: a memory-bound region wants traffic deleted, a launch-bound one wants kernels merged, a compute-bound one wants a better schedule for the math.

Bytes counts only what must cross the region’s boundary. The intermediate values bouncing through memory between ops are left out on purpose: they are the cost fusion hopes to delete, so they cannot be part of the ideal. That is also the answer to the second question above: each op alone can already be moving memory as fast as the chip allows and fusion still wins, because those ops were paying for intermediate traffic the fused limit does not include. And it is why glue next to a huge weight matrix prices out: when the deletable bytes are a rounding error next to the weights, s_max sits at 1 and pricing already dropped the region. A large region with almost no ceiling can still be opened; it just closes quickly if nothing beats the library.

Opening a region

Opening a region starts from what pricing already saved: the region’s real inputs and the library’s outputs for them. Those outputs are the reference every kernel the judge writes must match, and the reference is only ever measured from the library, never written by anyone. The time to beat, T_orig, is the region clock from pricing.

The judge does not start from a blank page. The harness first builds a scaffold: a working starting kernel to edit, stitched from the library’s own kernel source where possible (MLX ships it), otherwise generated as a plain, unoptimized kernel straight from the math. The scaffold must pass the full correctness ladder (next section) before the judge may touch it, because every hypothesis edits a kernel an earlier one produced, and iterating on top of a broken base wastes the whole region. If the generated scaffold cannot pass, the judge gets one attempt to fix it, and then the region is skipped. Passing does not make the scaffold a win: naive fused code is usually slower than the library. It is a correct starting point, nothing more.

From then on the region keeps two bookmarks. head is the kernel currently being edited: the best correct version so far, even if it is still slower than the library. shipped is the best version that is both correct and faster on the region clock; only shipped versions are ever installed into the model. A region opens with head at the scaffold and shipped empty, and the gap between them is normal: a slow-but-correct fusion stays head while its tiles are tuned until it finally beats the library.

As code:

ref      = saved_outputs[region]        # measured from the library, never written by anyone
scaffold = stitch_mlx_source(region) or lower_naive(region)
if not ladder(scaffold): scaffold = judge.fix(scaffold)     # one attempt
if not ladder(scaffold): skip(region)                       # never edit a broken base
head    = scaffold                      # the current editing base
shipped = none                          # best correct-and-faster; only this ever installs

What the judge is allowed to propose

The judge never sees tensors, weights, or activations. It is prompted with metadata: the region’s shapes and dtypes, p, which resource binds it (memory, compute, or launch), the source of the kernel it is editing, the last verdict, how far head and shipped sit from the roofline, and the menu below. It proposes one move at a time; nothing is generated in batches.

One clarification before the menu: whether ops merge is not on it. A multi-op region is one kernel by definition; that was decided when the region was built, and the scaffold is already that one kernel, just naively scheduled (stages back to back, intermediates still travelling through memory). The moves below are about making that kernel fast. They are common kinds, offered as suggestions: the judge names each hypothesis's kind in its own words and may propose any move the rules that follow allow, acting on what it sees in the region and its verdicts.

Common kinds:

  • Keep intermediates on-chip: hold values in registers or threadgroup memory between stages instead of letting them touch device memory. This is the move that makes a fused region pay.
  • Specialize launch and tiles for this workload’s shapes, without breaking other shapes.
  • Retile: change tile sizes, work per thread, SIMD-group layout.
  • Re-lay data out, as long as the layout round-trips exactly (swizzle, packing, cache order).
  • Same math, different algorithm: split-K, one-pass vs two-pass attention, persistent kernel, loop order.
  • Launch changes: grid, threadgroup size, threadgroup-memory budget.
  • Fix: repair whatever just failed to compile or match. Always legal.

Not allowed at all, whatever the kind is called: quantization or casts that the recorded ops do not already contain, approximate math (a cheaper softmax that is almost right), and anything that changes what the model computes. Fusing a quantize or cast that is already in the record is normal work; inventing a new one is not.

Every hypothesis carries one more tag, and it decides which correctness test applies later. Floating-point addition is not associative: add the same numbers in a different order and the last bits differ, without either answer being wrong. Some moves keep the arithmetic order exactly (fusing elementwise ops, layout and launch changes that leave reductions alone); their output should match the library almost bit for bit. Other moves reorder the arithmetic on purpose (split-K, retiling, loop order); their output is legitimately, deterministically different in the last bits. The first group is tagged assoc-preserving, the second assoc-changing. Reordering is not banned, and it is not waved through as noise either; the ladder gives each tag its own gate.

What crosses the boundary between harness and judge:

judge_sees:                      # metadata only; never weights or activations
  region:  shapes and dtypes, p, binding resource (memory / compute / launch)
  history: parent kernel source, last verdict, distance of head and shipped from roofline
  family:  assoc-preserving | assoc-changing
  menu:    the common kinds above, as suggestions; the rules are the only limit
  examples: worked replies, a few per call kind
judge_returns:
  a hypothesis queue in English  # Metal is written only for the front item

Hypothesis queue and conditionals

The judge plans in English and pays in Metal, one item at a time. It seeds a queue of hypotheses; only the front item is turned into an actual kernel. After each verdict it may insert, delete, or reorder, so nobody knows in advance how many hypotheses a region needs. The loop runs until the queue is empty (the judge has nothing left to propose) or a stop rule fires first (budget and plateau, in Closing a region).

Plans are conditional, and that is normal: “get the intermediates into registers,” then “if that is correct, retile K,” then “if it ships, unroll.” Failure branches too: “if three correct-but-slow schedules never beat the library, yield and let the smaller overlapping region take its turn.” Mutually exclusive families (one-pass vs two-pass attention) delete each other once one ships. What never happens is writing the retile before the kernel it depends on exists: a dependency names an earlier item and the outcome it needs.

A queue, concretely:

queue item:
  id:         h2
  kind:       retile                   # one of the menu; carries the assoc tag
  hypothesis: "tile K, 8 per thread"   # English, not Metal
  depends_on: h1                       # optional: an earlier item's id
  condition:  correct | shipped | failed

queue:
  - {id: h1, kind: on-chip, hypothesis: "keep the chain's intermediates in registers"}
  - {id: h2, kind: retile,  depends_on: h1, condition: correct, hypothesis: "tile K, 8 per thread"}
  - {id: h3, kind: launch,  depends_on: h2, condition: shipped, hypothesis: "then grid 256x4"}
  - {id: h4, kind: fix,     depends_on: h1, condition: failed,  hypothesis: "repair what broke"}

One hypothesis

The loop runs one hypothesis at a time. Executing one produces one small, evaluated change to a kernel, like one git commit: not an attempt at the whole kernel from scratch. A region’s work is the history of those commits, and the depends_on conditions in the queue read their verdicts.

Execution: take the front item whose condition is satisfied. The judge writes the kernel source and launch configuration as an edit of a parent, by default head, though it may name the scaffold or any earlier kernel. Parent is which code this change edits; depends_on is when it may run; two different things. Everything is then evaluated out of process with a timeout, because a hung or faulting shader must not take down the orchestrator; killing the process is how a wedged GPU recovers on this platform. Fast-math is pinned once per job and recorded (off, or whatever MLX itself ships), so correctness and timing compile the same math. Shader validation is on during the correctness stages and off during timing; validation recompiles instrumented pipelines, so smoke and determinism re-run on the exact un-instrumented pipeline that gets timed.

As code:

h = queue.pop_ready()                  # front item whose depends_on condition holds
kernel = judge.write(h, parent=head)   # one small diff of the parent, not a rewrite
in subprocess(timeout):
    result = ladder(kernel)            # the gates below, in order; first failure stops
verdict(h, result)                     # failed / correct-but-slower / shipped
judge.mutate_queue()                   # insert, delete, reorder

The ladder, in order

  1. Static checks, before anything runs. Inputs and outputs match the region’s in name, count, and rank. Dtypes identical. No new cast or quantization. Every live value is either still produced or listed as an output. A shape-specialized kernel declares its fallback to the library.
  2. Compile to a Metal pipeline, in the subprocess, with the pinned math flags.
  3. Poison the output buffers with NaNs before launch, so a kernel that writes only part of its output cannot pass on recycled memory. Out-of-bounds reads that happen to land on plausible values are why validation is on here.
  4. Watchdog on the first workload. Crash, hang, or slower than ten times the library’s region time is a fail.
  5. Smoke numerics on the first workload: every output compared under the gate in step 8, and finite unless the reference is not.
  6. The same, on every workload the region fires in.
  7. Shape sweep, correctness only, never speed. The named dims from the sweep policy move (1, a prime, a non-multiple of 32, one large size); integer dims never move. On every sweep shape the kernel must match, or, if it is shape-specialized, the log must show the fallback actually ran. Fast at 2048 and silently wrong at 7 tokens is a fail.
  8. Determinism, then the numeric gate. Run the first workload three times; the runs must match each other on both tags, because reordering is deterministic per binary and a racy kernel fails here no matter what else passes. Then, assoc-preserving: match the library within the manifest tolerance, floored by the library’s own run-to-run wobble. Assoc-changing: score the library and the new kernel against an fp32 golden of the same math, built from the same quantized weights dequantized to fp32 (fresh full-precision weights would make both errors quant-dominated and the gate meaningless); pass if err(new) ≤ κ · err(library) + floor, with κ around 1 to 1.5. Reordering accumulation is allowed; being sloppier than the library is not. The tag is a claim, not a verified property: claim preserving, fail the tight gate, and the hypothesis may resubmit as changing.
  9. Only then, the clock. Looped replay of the region, library and new kernel interleaved in the same session, ABBA so drift shows, baseline re-measured now and never reused. Faster means beating the library by more than max(1% of region time, 3σ of those samples), with the win times the region’s copies worth at least a few tens of microseconds per step. This is the ship clock; step time is not, because a 2× win on a 3% region is invisible there. The full model runs only at bind.

Verdicts: fail, climb, ship

Failed to compile or failed a gate: not shipped, not head. The kernel stays in the log with its failure, and it can still be a parent; the natural next hypothesis is a fix that names it, with condition: failed.

Correct but slower than the library on the region clock: not shipped, but it becomes head if its family is being climbed. This is the normal life of a fused region: the first correct one-kernel version usually loses, and then tiles, launch, and where intermediates live get tuned by further hypotheses until it wins. Nobody writes that sequence up front; each step reads the last verdict.

Correct and faster on the region clock: tentatively shipped, and head. Tentative because a region win is not yet a model win; bind and e2e decide that.

Bind and e2e promote

Shipping is not a flag in the harness. It is generating and installing a wrapper module: the harness emits code whose call replays the enclosing module’s recorded op sequence with the cut replaced by the new kernel and its recorded launch config, and swaps that wrapper in for the module on the live model. Shapes none of its kernels cover fall through to the original op sequence, which the wrapper also carries. Before a scope’s first ship, an identity form of the wrapper, the same replay with no kernel change, must be indistinguishable from the original everywhere the scope fires; a scope that cannot pass that has no install point. Then retrace the patched model. The intercept log must show that cut became one custom dispatch and that neighbors are unchanged. If it does not, bind failed and the ship is rolled back. That check is what makes e2e mean anything; without it we would be benchmarking orphaned kernels.

E2e gets its own metric, not the single-op tolerance. Run the original model twice on the workloads to get an original-vs-original floor (max abs, plus cosine or KL on the outputs). Compare patched vs original against that floor. After thirty layers of swapped kernels, per-op tolerances false-fail; error compounds. Assoc-preserving ships should sit on the noise floor, and a large miss means the bind installed the wrong cut. Assoc-changing ships use the golden-relative rule, with weights kept quantized and activations run in fp32 so the golden fits in memory at 8B.

Step time at e2e is a non-regression veto, not the detection gate: the patched step must not be significantly slower than the original under the same interleaved discipline. Failing e2e or failing bind rolls the ship back, and the judge mutates the queue: prepend a fix, drop a family, or take the failure branch.

Closing a region

A region does not close because it reached perfection; it closes because the next region deserves the budget more. The first shipped win usually marks the start of tuning, not the end of the region.

tracked per region:
  hypotheses run, fail streak on one parent, size of recent ships,
  family being climbed, head's clock vs the roofline

close when any:
  the region's hypothesis budget is spent          (budget.per_region)
  5 straight compile or static fails on one parent
  shipped is within 5% of the roofline
  3 ships in a row, each under 2% better than the last
  6 hypotheses in a row that beat shipped by neither 1% of region
    time nor tens of microseconds per step across the copies
  head's clock minus the roofline is under ~1% of the step
  the queue is empty                               (the judge yields)
  the job budget is spent                          (budget.total)

Climbing a slow family is a sub-state, not a close: correct-but-slower keeps updating head and still counts as progress. It stops counting when the family looks hopeless, eight correct-but-slower attempts without ever beating the library. Then the family is abandoned, head resets to the scaffold or the last shipped kernel, and the queue moves on to its next family; if this region never ships at all, the smaller overlapping regions get their turn. If nothing has shipped and every family is abandoned, close.

Leaving a region, and the artifact

Closing ends the region, not the job. The trace passes re-run on the patched model: the step got shorter, so every remaining region’s share updates, and regions whose ops are now covered by a shipped bigger cut are dropped. Then the next region opens.

When the regions or the budget run out, one last end-to-end check runs on the workloads, plus a sweep pass confirming that every shape-specialized kernel’s fallback still engages. Then the job writes the artifact, which works without the harness:

artifact/
  kernels/      one .metal + launch config per shipped kernel
  wrappers      the generated patch module: readable code, explicit kernel calls
  swap_table    scope -> wrapper, region -> kernel, fallback rule per shape
  apply()       swaps the generated wrappers onto a freshly loaded build() model
  report        per region: p, s = T_orig / T_shipped, step before / after
                per hypothesis: id, kind, parent, verdict, failed gate, region ms

That is the whole job. Nothing in it assumes an architecture: the recorded ops decide the regions, the judge invents the next change, the harness decides whether it is real, and what is left behind runs without any of this machinery.

Flow recap

The whole job, one screen, using the pieces defined above:

# job
model = import(manifest.model).build()            # tracer installed before any model import
for w in workloads:
    trace[w]   = record(model, w)                 # pass 1: lazy, no eval, completeness-checked
    step_ms[w] = median(evals(model, w))          # pass 2: recorder removed

# regions
candidates = [group_copies(seq) for seq in singletons + chains if not rejected(seq)]
save_boundaries(candidates)                       # one recorded pass per workload
price_and_rank(candidates)                        # region clock, roofline, floor, bound

# the loop
for region in ranked:
    scaffold = stitch_mlx_source(region) or lower_naive(region)
    if not ladder(scaffold): skip(region)         # after one judge fix attempt
    head, shipped = scaffold, None
    queue = judge.seed(region_metadata)
    while queue and not close_rules_fire(region):
        h      = queue.pop_ready()                # depends_on condition satisfied
        kernel = judge.write(h, parent=head)      # one small diff
        result = subprocess(ladder, kernel)       # gates 1..9; first failure stops
        if   result.failed: log(h)                # a fix may name it later
        elif result.slower: head = kernel         # climb
        else:                                     # faster on the region clock
            bind(region, kernel)                  # generated wrapper swapped in at its scope
            if retrace_shows_one_dispatch() and e2e_on_floor():
                shipped = head = kernel
            else:
                unbind(kernel)                    # original module swapped back
        judge.mutate_queue()
    retrace(model)                                # shares update; covered regions drop

# out
final_e2e(workloads); verify_fallbacks(sweep)
emit(kernels, wrappers, swap_table, apply, report)

And a typical history on one region (times illustrative):

h1  on-chip     compile error: threadgroup memory over budget      failed
h2  fix(h1)     correct, 8.1 ms vs library 6.7 ms                  head
h3  retile(h2)  correct, 5.9 ms                                    tentative ship
    bind: one custom dispatch, neighbors unchanged; e2e on floor   shipped
h4  unroll(h3)  correct, 5.7 ms                                    shipped
h5  launch(h4)  5.72 ms, no win                                    not shipped
    plateau: close

That story is not a plan. The retile hypothesis did not exist until the fix had a verdict, and nothing entered the model until bind confirmed the cut was the cut. The judge invented each next step from the last result; the harness decided what was real.

Future additions

Three additions are designed but deliberately out of v1. None of them needs machinery the sections above did not already build, and each is a pattern similar systems have proven out on the CUDA side. They are cut for scope, not for risk.

Precompute, a future kind for the menu: a value that depends only on weights and constants does not need to be recomputed every step. It can be computed once when the artifact is applied and stored alongside the kernels. Packed weight scales, the concatenated weight a merged projection kernel wants, frequency tables: all weight-only work, and the trace can find it mechanically, because the record already knows which arrays are weights. The math is unchanged, so the usual gates apply; the only new machinery is a slot in the artifact for stored buffers, and apply() filling it at load.

Reuse, a future harness transform: when one record contains the same ops run on the same actual arrays twice, the second copy is free. Detection is mechanical, since the trace records array identities, and the replay rewriting that bind already uses is exactly the tool for handing the first stretch’s outputs to the second’s consumers. The canonical case is classifier-free guidance in diffusion models: the denoiser runs twice per step with different prompts, and the branches that depend only on the timestep compute identical values in both passes. Like region enumeration this is found by rule, not proposed by the judge, and a reuse ships through the same checks a kernel does: outputs compared, bind retraced, e2e on the floor.

A memory across jobs: today every job starts from zero. Shipped kernels could be retained as starting scaffolds for matching regions in later jobs, and verdicts distilled into guidance the judge reads when a region opens. Purely additive, and worth building only once there are enough jobs for the memory to matter.

Sketched:

precompute:                     # a future kind for the menu
  detect:  stretches whose inputs are all weights or constants
  ship:    run once when the artifact is applied; store the buffers with it
  gate:    math unchanged; the usual gates apply

reuse:                          # a future harness transform, found by rule
  detect:  same op sequence on the same actual arrays, twice in one record
  ship:    the wrapper substitutes the first stretch's outputs for the second's
  gate:    outputs compared, bind retraced, e2e on the floor

memory:                         # framework, not a kind
  keep:    shipped kernels as starting scaffolds for matching regions in later jobs
  distill: verdicts into guidance the judge reads when a region opens
